Overview

Fleet Commander is an IoT fleet management module built by IoT-Forge — a suite of interconnected IoT products. It provides a complete backend for managing fleets of connected devices: registration, heartbeat monitoring, remote configuration via MQTT, over-the-air (OTA) firmware updates with automatic rollback on failure, AI-powered fleet analytics, and a full alerting pipeline.

📡

MQTT Command & Control

Bi-directional communication with devices over MQTT topics. Publish OTA commands, remote configs, and receive heartbeats.

🔄

OTA with Rollback

State-machine driven firmware updates. Hash mismatch detection triggers automatic rollback to previous firmware version.

🤖

AI Agents

Phase 1 Crew AI agents for OTA campaign planning, anomaly detection, device grouping, device onboarding, and V2G arbitrage.

📊

Full Observability

Prometheus metrics (fleet size, OTA deploys, API latency, MQTT throughput) + pre-built Grafana dashboards.

🔔

Alerting Pipeline

Active alert system with dedup, cooldown, escalation, and multi-channel delivery (Slack, Email, Webhook).

⚡

V2G Arbitrage

Vehicle-to-Grid optimizer schedules EV battery charge/discharge to maximise revenue, accounting for battery degradation cost.

Device Management

Devices auto-register on their first MQTT heartbeat or can be registered manually via the REST API. Each device tracks firmware version, IP address, MQTT client ID, signal strength, uptime percentage, and online/offline status.

Auto-Registration

When a device sends its first heartbeat to the iot/fleet/register topic, the backend automatically creates a device record. Devices are identified by their MQTT client ID for deduplication.

Heartbeat Monitoring

curl -X POST http://localhost:8181/devices/{device_id}/heartbeat \
  -H "Content-Type: application/json" \
  -d '{"uptime_percentage": 99.2, "signal_strength": -58}'

Heartbeats include uptime percentage, signal strength (dBm), and for EV devices: state of charge (SOC), state of health (SOH), battery temperature, and plug status. Devices not seen for 60+ seconds are marked offline.

OTA Firmware Updates

The OTA (Over-The-Air) update system uses a formal state machine with automatic rollback on failure. The backend tracks every deployment and provides real-time status via the dashboard and API.

State Machine

pending → downloading → applying → verifying → success
→ hash_mismatch → rollback → rolled_back
→ failed (timeout / max retries)

Upload & Trigger

# Upload firmware binary (auto-generates SHA256 hash)
curl -X POST http://localhost:8181/ota/upload \
  -F "version=2.0.0" \
  -F "file=@firmware.bin"

# Get the firmware ID from response, then trigger:
curl -X POST http://localhost:8181/ota/trigger \
  -H "Content-Type: application/json" \
  -d '{"firmware_id": "<FW_ID>", "all_devices": true}'

Rollback on Hash Mismatch

When a device reports hash_mismatch after applying firmware, the backend automatically: (1) logs the failure, (2) sets the deployment status to rolled_back, (3) reverts the device's firmware to its previous version. The simulator has a configurable 20% failure rate to demonstrate this behavior.

All device communication happens over MQTT topics under the iot/fleet/ hierarchy.

Remote Configuration

Configuration can be pushed to individual devices via MQTT or REST API. The system publishes to iot/fleet/{id}/command/config and logs device acknowledgement. 

curl -X POST http://localhost:8181/devices/{device_id}/config \
  -H "Content-Type: application/json" \
  -d '{
    "heartbeat_interval_seconds": 10,
    "ota_poll_interval_seconds": 60,
    "log_level": "INFO"
  }'

Alerting & Notification Pipeline

The alerting system converts passive anomaly detection into active, actionable alerts with full lifecycle management, deduplication, cooldown periods, escalation, and multi-channel delivery.

Alert Lifecycle

active → acknowledged → resolved

Alert Channels

  • Slack — Webhook integration
  • Email — SMTP-based delivery
  • Generic Webhook — Custom HTTP endpoint

Phase 1 Crew AI Agents

Fleet Commander includes four AI agents that run in either in-backend mode (direct SQLAlchemy) or CLI mode (HTTP-based), avoiding self-referencing deadlocks in the single-worker FastAPI process.

OTA Campaign Agent

Generates canary-based rollout plans: canary → Phase 1 (30%) → Phase 2 (60%) → Phase 3 (100%) with pass/fail gates between phases.

Anomaly Detection Agent

Scans for weak signals, stuck OTAs, failure spikes, offline devices, and V2G revenue drops. Reports structured findings with severity.

Device Group Manager

Groups devices by firmware version cohorts and signal strength buckets (Good / Moderate / Poor) for targeted rollouts.

Device Onboarding Agent

Guides new device introduction with conflict checking, firmware recommendation, auto-registration, and heartbeat verification.

REST API

# Run all agents
curl http://localhost:8181/agents/recommendations

# OTA campaign for a firmware
curl 'http://localhost:8181/agents/ota-campaign?firmware_version=2.0.0'

# Anomaly check
curl 'http://localhost:8181/agents/anomaly-check'

# Device groups
curl 'http://localhost:8181/agents/device-groups'

# Fleet health (triggers alerts)
curl 'http://localhost:8181/agents/fleet-health'

CLI Runner

# Run all agents
python run_agents.py

# OTA campaign only
python run_agents.py --ota --firmware 2.0.0

# Anomaly check
python run_agents.py --anomaly

# JSON output
python run_agents.py --json | jq .

Device Onboarding Agent

The Device Onboarding Agent guides operators through introducing new devices into the fleet. It supports both recommendation mode (dry-run with plan) and auto-register mode (full automated onboarding).

Operator submits device name │ ▼ Device Onboarding Agent 1. Check name/MQTT ID conflicts ──► Database lookup 2. Recommend latest firmware ──► Firmware list 3. Generate initial config ──► heartbeat interval, OTA poll 4. Register device (if approved) ──► INSERT Device + metrics 5. Push MQTT config ──► publish_remote_config 6. Verify first heartbeat ──► Check last_seen │ ▼ Onboarding Report (JSON → CLI / Dashboard UI)
# Recommendation mode (read-only plan)
curl 'http://localhost:8181/agents/onboarding?name=Sensor-042'

# Auto-register mode
curl 'http://localhost:8181/agents/onboarding?name=Sensor-042&auto_register=true'

# Via CLI
python run_agents.py --onboard "Sensor-042" --onboard-auto

V2G Arbitrage Optimizer

The V2G (Vehicle-to-Grid) arbitrage module schedules EV battery charge/discharge to maximize net revenue, accounting for battery degradation costs. It uses a heuristic optimizer over a configurable time horizon.

Battery Degradation Model

The degradation cost per kWh cycled is computed as:

C_deg = replacement_cost × base_fade_per_cycle / capacity × SOH_factor × temp_factor
  • SOH_factor: (80% / SOH)² when SOH < 80%, otherwise 1.0
  • Temp_factor: Arrhenius model — doubles every 10°C above 25°C
  • No discharge allowed when SOH < 70%
  • Default replacement cost: $35,000 (configurable)

Security & Dependency Management

All Python dependencies are pinned to exact versions in requirements.txt. Dependabot is configured for automated vulnerability alerts on the GitHub repository.

Recent Hardening (Session 2)

11 packages were upgraded to patch known CVEs, including critical fixes:

  • python-multipart — Path traversal → RCE (CVSS 8.6)
  • jinja2 — Sandbox escape (CVSS 8.8)
  • requests — Credential leak via session certificate bypass
  • pytest — Local tmpdir privilege escalation

All 3 Dockerfiles were hardened with apt-get upgrade -y at build time and include cleanup of package lists to reduce attack surface.

Production Scaling

For larger deployments, Fleet Commander supports several scaling strategies:

PostgreSQL

Switch from SQLite to PostgreSQL via DATABASE_URL. Use the production Docker Compose profile.

Backend Scaling

Horizontal scaling behind a reverse proxy: docker compose up -d --scale backend=3

MQTT Clustering

Replace single Mosquitto node with a cluster or use a managed MQTT service (e.g., HiveMQ, AWS IoT Core).

S3 Firmware Storage

Mount an S3-compatible bucket or NFS volume instead of the local Docker volume for firmware binaries.

Prometheus Retention

Increase retention period and add alerting rules for device offline events and anomaly thresholds.

Advanced Optimization

TimescaleDB hypertables for time-series SOC/SOH data. MILP via PuLP/OR-Tools for stochastic V2G optimization.
